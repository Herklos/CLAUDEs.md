# i18n — tips, gotchas & reference notes

Curated from real debugging sessions and a full-app localization sweep on a
React app with English source strings and a French target locale. Organized
by the kind of mistake, because every entry here shares one property:

> **The bug is invisible in the source locale.** English reads perfectly. The
> reviewer approves. The French build is broken.

That's what makes these expensive — the normal review loop cannot catch them.

## Composing with formatters

### A translated connector word can silently duplicate the formatter's own output

The headline entry of this file.

A relative-time helper returns localized strings. Its English messages look
like fragments — `"8 days ago"` — so call sites naturally prepend their own
translated connector:

```tsx
{t('added-prefix')} {formatRelativeTime(node.addedAt)}
// en: "added" + "8 days ago"      → "added 8 days ago"     ✅
// fr: "ajouté il y a" + "il y a 8 jours" → "ajouté il y a il y a 8 jours"  ❌
```

The French messages are **complete phrases** — `"il y a {count} jours"`
already contains "il y a". The English source never shows the bug, because
English puts "ago" as a *suffix* on the formatter's side, while French puts
"il y a" as a *prefix* on the same side the caller is also prefixing. Three
separate call sites made this identical mistake independently.

**Rule**: when composing a label with the return value of any
`formatRelativeTime` / `formatDate` / `formatDistance`-style helper, check
what that helper's own string already contains **for the target locale** —
not for the source locale.

**Generalizes**: a fix validated only against the source locale can be
verifiably correct there and still be broken everywhere else, because
languages disagree about *which side of the phrase* a given piece of meaning
lives on. Grammatical structure is not portable across locales; string
concatenation assumes it is. Prefer handing the whole phrase to the
formatter (or to one ICU message) over gluing a translated prefix onto a
translated result — every seam between two translated strings is a place
where two locales' grammars can disagree.

## What counts as translatable

### The PLACEHOLDER trap

A local `const PLACEHOLDER = {...}` **does not mean "skip translating"** — but
that's exactly how it reads to every subsequent reader, including the person
who wrote it.

A full-app sweep found several real, functional, reachable screens (a
notification-settings page, an assumptions page, a multi-step install wizard)
where *every* string — live labels, banners, and the text on interactive
buttons — was hardcoded English under a `PLACEHOLDER` const. The name had
quietly granted the whole file an exemption it never earned.

**Rule**: check what the const actually *holds*.

- Genuinely fake/decorative **data** — a fake hostname, a fake checksum, fake
  log lines, mock tickers, mock formatted numbers — stays hardcoded. You
  translate UI, not fake data.
- The **chrome around it** — labels, eyebrows, banner sentences, button text,
  accessibility labels — needs real translation keys regardless of what the
  enclosing const is named.

**Generalizes**: a variable name is a claim about intent, and stale claims
outlive the intent. `PLACEHOLDER`/`MOCK`/`TEMP` naming makes reviewers skip
the contents — which is useful right up until the mock ships. If a screen is
reachable in the product, audit it by what it *does*, never by what its
constants are called.

### An id is not a name

A bot edit-flow review screen rendered a literal internal account id
(`exchange_1783410893737`) where the account's real name belonged. Nothing
was hardcoded; the data was correct; no translation key was missing. Nobody
had resolved the id to a display name.

**Rule**: any screen that shows "here's what's about to happen" for an
id-referenced entity (account, node, space, strategy) must resolve that id to
its live display name through the owning store's hook — not print the id.

Worth listing with i18n bugs because it's the same failure at heart: a string
reaching a user that was never meant for a user to read.

## Translating values you don't own

### An SDK that ships English name literals is right — translate on your side

A UI-agnostic SDK ships builtin entity names ("Investor", "Semi-pro
Trader", ...) as plain English strings, deliberately: it has no i18n
dependency and shouldn't. That's a correct design, not a bug to fix upstream.

**Fix**: translate on the app side via a dedicated message namespace, with a
hook that maps the SDK's value to a key. Never patch the SDK.

### Only translate while the value still exactly matches the default

The critical rule, and it applies to every "translate a name that might be
user data" case:

**Translate only if the value *still exactly matches* the untouched default.
The moment a user renames it, it is real user data and must never be
re-translated.**

The same rule covers the fork/copy edge case: if touching a builtin produces
a *forked* copy (new id, `basedOn` pointer set), translate that fork's name
only while it still matches the original's name verbatim. The instant it
diverges, hands off.

This applies well beyond SDK values — the same conditional-translation guard
belongs on any catalog-derived label that's also user-renamable:

```ts
// a node's label is real, persisted, user-renamable data
label === catalogDefault.label ? t(`${key}.label`) : label
```

**Generalizes**: "is this string content or data?" is not a property of the
field — it's a property of the field's *current value*. The same column holds
a translatable default on Monday and untouchable user data on Tuesday. Guard
on equality-with-default, not on the field's name or type. Getting this
backwards means translating a user's own words back at them, which is worse
than not translating at all.

## Missing keys

### A missing translation renders the key and nothing fails

i18next's miss behaviour is to **return the key**, so a screen ships reading

```
settings.premium
```

where a sentence should be. No throw, no console warning, no red screen. It
survives code review (the call site is correct), it survives typecheck (the
key is a string), and it survives QA in the default language — because the
default language is the one locale that is complete. It only appears to users
of the locale nobody on the team reads.

**Fix**: a parity test, not vigilance. Walk both catalogues and assert the key
sets are identical.

```ts
// Flatten each locale to dotted leaf paths, then diff the sets.
expect(keysOf(en)).toEqual(keysOf(fr));
```

`Generalizes:` any lookup whose miss path returns a *plausible value* instead
of failing (i18next→the key, a `?? 'default'`, a permissive `Proxy`, a
`defaultdict`) converts a loud bug into silent wrong output, and moves
detection from your machine to your users. The absent test is the real defect.
When a library's miss is non-fatal by design, the completeness check is
**yours** to write, and it belongs in CI rather than in a checklist.

## Where to apply the translation

### Translate at the single source that feeds every render site

When several screens render the same entity, resolve the localized text in
the one memo/selector that builds the shared list, not in each screen.

Applying the catalog lookup inside the single `nodes` memo automatically
cascaded the fix to the canvas, the inspector, and the quick-edit sheet.
Applying it per-screen would have been three fixes, three chances to miss
one, and permanent drift.

The corollary is a review heuristic: **if a translation fix has to be applied
in more than one place, you're fixing it at the wrong level.** Find the
shared source. And when a hook wires up N render sites, any *new* render site
must call the hook too rather than reading the raw field — worth stating
explicitly in the code's own docs, since the raw field stays temptingly
available.

Related: if a types file's own header comment promises a localization hook,
verify the hook exists. One did not, for a long time, and every reader
assumed it did because the comment said so.

## Conventions worth keeping

- **Everything user-readable is in scope**: titles, subtitles, eyebrows,
  button labels, placeholders, alert/banner copy, accessibility labels,
  segment/filter labels, badge text, error fallbacks. If a user can read it,
  it needs a key — and an entry in *every* locale file, not just the source.
- **Static config holds keys, not text.** Config that carries user-facing
  strings (step titles, kind labels) stores `*Key` fields and resolves via
  `t(...)` at render. A config object is not a rendering context and has no
  locale.
- **ICU interpolation and plural forms over string concatenation** —
  `{count}`, `{name}`, plural categories. This is the same lesson as the
  formatter entry above, in its preventive form: every concatenation seam is
  a grammar assumption, and ICU exists so the message file can own the
  grammar instead of the code.

## Translator identity in React effects

### A scheduled side effect keeps cancelling and re-running because the translator function is in its deps

A hook that (re)schedules a local notification listed the `use-intl`
translator function itself in the effect deps (`[tl, ...]`). `useTranslations`
returns a *fresh function identity* on some renders, so the effect tears down
and re-runs on renders where nothing meaningful changed — the notification is
cancelled and rescheduled in a loop.

**Fix**: resolve the strings *outside* the effect and depend on those:

```ts
const title = tl('notif-title');
const body = tl('notif-body');
useEffect(() => { /* schedule with title/body */ }, [title, body, ...]);
```

Strings compare by value, so the effect re-runs only on a real locale change —
the one time the scheduled copy is actually stale.

**Generalizes**: never put a library-returned *function* in effect deps unless
its docs guarantee referential stability. Depend on the resolved values the
effect actually uses; they carry exactly the change signal you want.
